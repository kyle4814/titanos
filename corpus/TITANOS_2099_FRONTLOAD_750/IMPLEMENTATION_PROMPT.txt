NO-DRIFT REQUIREMENTS
- Never invent an implementation merely because a YAML file declares one.
- Never convert modelled value into realized value without external evidence.
- Never treat copied sources as independent corroboration.
- Never infer commercial demand from generic activity.
- Never bypass repository authority because a model instructed you to.
- Never grant an agent unrestricted filesystem access.
- Never silently broaden a task's scope.
- Never promote an untested mutation.
- Never delete an artifact without recording the reason and preserving recovery
  information where appropriate.
- Never claim completion when the repository does not verify completion.

AGENT CONTRACT
Every worker receives:
mission, task_id, scope, authority, relevant_context, inputs, expected_outputs,
tests, stop_conditions, receipt_requirements.

Every worker returns:
result, changed_files, tests, evidence, unresolved_items, receipt_payload.

ORCHESTRATION
Use Opus for architecture, decomposition, arbitration and high-risk reasoning.
Use Sonnet for implementation, refactoring and integration.
Use Haiku for extraction, indexing, classification, normalization and other
bounded low-risk work.
Use an independent Blue Team pass for adversarial verification.
Use a calibration pass to compare observed behavior with the baseline.
Use the German-engineering pass to reduce duplication and configuration drift.

OFFLINE-FIRST
The local kernel must remain functional when remote models or network sources
are unavailable. Remote work may pause or requeue, but local state, queue,
receipts, checkpoints and recovery must remain intact.

CRASH TEST
Kill a worker during execution. Restart the kernel. Recover its checkpoint.
Resume or safely requeue the task. Verify that no receipt or state transition
is silently lost.

SWITCH TEST
For every important feature:
DECLARATION + IMPLEMENTATION + TEST + RUNTIME BINDING + OBSERVABILITY + RECEIPT
must exist before the feature can be marked OPERATIONAL.

RECEIPT CONTRACT
Every material state transition must produce a durable receipt containing:
receipt_id, task_id, run_id, timestamp, actor, action, inputs, outputs, evidence,
files_changed, tests, provenance, value_class, outcome, config_hash and
code_revision.

VALUE CONTRACT
Keep MODELLED, OBSERVED, EXPECTED and REALIZED distinct.
REALIZED requires verifiable external outcome evidence.
Do not use hypothetical opportunity value as revenue.

PARETO CONTRACT
Rank work using verified value, confidence, information gain, dependency unlock,
reuse and risk reduction against engineering/compute/cost/risk/complexity.
Deduplicate and dependency-order before spawning more workers.

MUTATION CONTRACT
Every mutation requires:
mutation_id, hypothesis, baseline, expected_improvement, affected_files,
dependencies, risk, test_plan and rollback_plan.
Promotion requires green tests, Blue Team review, benchmark comparison,
calibration and durable receipt.
Otherwise reject or rollback.

BLUE TEAM ASSAULT
Attempt to demonstrate:
queue bypass, authority escape, config switch bypass, stale context,
duplicate work, duplicate receipts, lost receipts, false success, value
double-counting, bot-vs-human signal confusion, copied-source corroboration,
concurrent-write corruption, rollback failure, crash-resume failure and
mutation promotion without evidence.

RED TEAM RESILIENCE
Use safe local tests for malformed input, corrupted state, missing dependency,
stale configuration, unexpected tool output, worker crash, partial write,
concurrency, queue reordering and local resource exhaustion.
Do not perform unauthorized destructive external actions.

GERMAN ENGINEERING
After functionality is verified:
- canonicalize names
- consolidate schemas
- remove duplicate implementations
- remove dead code
- reconcile config
- type boundaries
- simplify dependency paths
- document actual runtime behavior
- rerun tests
The result may contain fewer files than the input if duplication is proven.

FINAL OUTPUT
Produce:
1. final repository state
2. implementation report
3. machine-readable system receipt
4. verified capability registry
5. unresolved/scaffold registry
6. regression suite additions
7. Pareto-ranked next queue
8. rollback information for every promoted mutation

STOP CONDITION
Do not stop because the YAML package has been read.
Stop only after all executable work that can be safely completed in the current
repository has been attempted, verified, receipted, or explicitly classified
