## Title

Documentation gap: the SGSP hardness assumption that the election-event
seed constraint protects is never named in the System Specification, the
Verifier Specification, or the crypto-primitives source

## Severity

**Low / Informational — documentation.** This is not a vulnerability. The
control works and is enforced. The finding is that a load-bearing
security *rationale* is recorded only outside the specification and code.

## Summary

Vote privacy in the Swiss Post system rests, in part, on the **Subgroup
Generated by Small Primes (SGSP)** problem — which Swiss Post's own
commissioned analysis (Gaudry, CNRS/LORIA, `Protocol/sgsp.pdf`, May 2022)
flags as "studied less in the academic literature than DDH." The property
that keeps SGSP hard in practice is that the prime `p` is *provably
randomly generated*: the seed to `GetEncryptionParameters` is public and
tightly constrained (the election-event name, format `CT_YYYYMMDD_XYnm`),
leaving at most ~99 candidate primes for a fixed canton and legally-fixed
date — far too few for an adversary to grind a special-form prime.

**That constraint is real and enforced** (System Specification §3.2 fixes
the format; Verification 5.01 recomputes `(p,q,g)` from the seed;
`EncryptionParameters.getEncryptionParameters` derives `q` from
`shake256(seed)`). **But nowhere in the specification or the code is it
documented that this seed constraint is what defends the SGSP
assumption.** The only place that rationale exists is Gaudry's note, which
is not part of the spec or the codebase.

## Evidence — computed, not eyeballed

Term trace for `SGSP` across the four reachable documents:

| Document | SGSP mentions |
|---|---:|
| System Specification v1.6.1 | **0** |
| Verifier Specification v1.7.1 | **0** |
| crypto-primitives source + docs | **0** (one grep hit is a base64 test-fixture false positive) |
| Gaudry commissioned note (`Protocol/sgsp.pdf`) | 20 |
| Computational-proof documents | 43 |

The `getEncryptionParameters` javadoc documents only the *reproducibility*
property ("executions with the same seed yield the same encryption
parameters", "seed = the name of the election event") — never that the
public, constrained seed is what prevents an adversary constructing a
special-form prime.

**SGSP is the outlier, not the pattern.** Every other named assumption
from the protocol's own Limitations section *is* discussed in the System
Specification — quantum adversaries (3), malicious client (2), trustworthy
setup (1), trust assumptions generally (7), vote secrecy (10). SGSP is the
single named assumption the specification never mentions, and it is also
the one Swiss Post itself flags as least-studied, and the one whose
protection is a restriction written into that very specification.

## Why it is worth fixing

A load-bearing security property is presented as a formatting rule. The
only rationale §3.2 gives for the `CT_YYYYMMDD_XYnm` format is
modulo-overflow prevention — about the *size* of the primes, not the
*unpredictability* of `p`. This is precisely the shape of thing a future
revision relaxes (a longer sequence field, free-text event names) without
anyone realising what it was holding up.

## Suggested remediation

One sentence closes it permanently: a cross-reference in System
Specification §3.2 (and in the `getEncryptionParameters` javadoc) stating
that the public, constrained election-event seed is what keeps the SGSP
assumption hard by bounding the number of candidate primes an adversary
can search, citing the Gaudry note.
