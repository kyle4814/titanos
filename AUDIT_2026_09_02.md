## FINDING 1 (HIGH) — four of the eight mouths built this session have zero production callers

`mouth_find_a_tender_uk.py`, `mouth_etenders_ie.py`, `mouth_bounty.py`,
`mouth_gigs.py` each have a `sweep()` function, real tests, and a
careful docstring describing live-verified findings — but nothing in
this repository ever calls them outside their own test files.

**Reproduction:**

```
$ grep -rln "mouth_find_a_tender_uk\|mouth_etenders_ie\|mouth_bounty\|mouth_gigs" foundation/*.py foundation/tests/*.py
foundation/mouth_bounty.py
foundation/mouth_etenders_ie.py
foundation/mouth_find_a_tender_uk.py
foundation/mouth_gigs.py
foundation/tests/test_mouth_bounty.py
foundation/tests/test_mouth_etenders_ie.py
foundation/tests/test_mouth_find_a_tender_uk.py
foundation/tests/test_mouth_gigs.py
```

Only the module itself and its own test file mention each name — no
other `.py` in the repository imports any of the four.

Checked every plausible entry point:
- `foundation/sources.py::ALL_SOURCES` = `(TED, NZ_GETS, UK_CONTRACTS_FINDER)`
  only (`sources.py:430`) — none of the four new mouths are registered
  as a `Source`, so `hunt_multi()` can never reach them.
- `foundation/operator_cli.py` subparsers are exactly `hunt`, `brief`,
  `loop`, `dossier`, `profile` (`operator_cli.py:427-451`) — no
  subcommand for any of the four sources, and no import of any of
  their modules anywhere in the file (`grep -n "import" operator_cli.py`
  shows only `foundation.sources.sources_for_query`).
- `foundation/cron_pulse.py` — the file that `CLAUDE.md` itself names
  as "the only clock" — schedules exactly two mouths:
  `MOUTHS = [(mouth_pypi..., ...), (mouth_github_releases..., ...)]`
  (`cron_pulse.py:55-58`). Not even `mouth_ted`/`mouth_gets_nz`/
  `tender_radar` are on this clock, let alone the four newest ones.

**Why this is a real defect and not "legitimately unwired":** none of
the four is a human-authority gate (the honest unwired case this repo
otherwise has, e.g. `publication_gate`). They are pure read-only
observation mouths — the same shape as `mouth_pypi`/`mouth_github_releases`,
which ARE wired to `cron_pulse.py`. There is no doctrine reason these
four should be inert; they are simply not connected yet. The result:
`RESOLVED_TARGETS.md` (dated 2026-09-02, same day) presents live
findings sourced from `find-tender.service.gov.uk` and `etenders.gov.ie`
as things a human resolved by hand — which is accurate for that document
— but nowhere does any `.md` or code comment tell an operator that
running `operator_cli.py hunt` or `loop` will never surface a single
item from these two sources, or from the bounty/gigs mouths. An
operator who reads `mouth_find_a_tender_uk.py`'s docstring (live
notices, deadlines, values, all confirmed) and then runs `hunt --live`
expecting to see Bradford MDC or NHS England in the output will get
nothing, silently — the CLI has no error path for "you asked for a
source that isn't registered" because there is no way to ask for it at
all.

**Fix scope note (not performed — audit only):** wiring these four into
`sources.py`'s `Source` registry (each would need a TED-shaped
normaliser respecting `sources.py`'s own CRITICAL HONESTY RULE, since
none of the four are procurement-criteria sources in the same sense —
`mouth_bounty`/`mouth_gigs` in particular are not procurement notices at
all and may not belong in the qualification pipeline the same way;
`mouth_find_a_tender_uk`/`mouth_etenders_ie` plainly do) is real,
non-trivial work, correctly out of scope for this audit.

## FINDING 2 (MEDIUM) — the unattended `loop` command is silently TED-only, while `hunt`/`brief` are three-source

`operator_cli.py::cmd_hunt` and `cmd_brief` both call `_run_hunt()`,
which builds `sources_for_query(...)` (TED + NZ_GETS + UK_CONTRACTS_FINDER)
and calls `hunt_multi()` (`operator_cli.py:265-267`).

`operator_cli.py::cmd_loop` calls `run_hunt_loop()`
(`operator_cli.py:330-334`), which calls `run_one_hunt_cycle()`
(`hunt_loop.py:434-440`), which calls `foundation.hunt.hunt()` —
the **single-source, TED-only** function
(`hunt_loop.py:70`: `from foundation.hunt import HuntEntry, HuntReport, hunt`
— not `hunt_multi`).

**Reproduction:** `grep -n "hunt_multi" foundation/hunt_loop.py` returns
nothing; `grep -n "^from foundation.hunt import" foundation/hunt_loop.py`
shows only `hunt` imported.

**Consequence:** an operator who runs `hunt`/`brief` interactively sees
NZ GETS and UK Contracts Finder notices; the same operator running
`loop --live` for continuous unattended monitoring will never see a
notice from either source, ever — not because they're filtered out, but
because `run_one_hunt_cycle()` never fetches them. This is not hidden —
`cmd_loop`'s own dry-run print and its constructed `objective` string
both say "against TED" (`operator_cli.py:306-308`) — but it is not
documented as a limitation anywhere in `hunt_loop.py`'s own module
docstring (which instead says "`hunt.py::hunt()` is the only place
notices are fetched", true but doesn't flag that this specific choice of
`hunt()` over `hunt_multi()` silently narrows the loop's source
coverage relative to the other two commands built in the same session).
`foundation/tests/test_hunt_loop.py` never asserts or documents this
scoping either (`grep -n "hunt_multi\|NZ_GETS\|UK_CONTRACTS" tests/test_hunt_loop.py`
returns nothing) — so nothing in the test suite would catch a future
change that made this asymmetry worse, or a future reader's assumption
that `loop` has the same source coverage as `hunt`/`brief`.

**Severity note:** lower than Finding 1 because the CLI is at least
honest in its printed output at the point of use — an operator reading
the dry-run text before going `--live` would see "against TED" and
could reasonably infer the narrower scope. It's still a real
inconsistency an operator could miss, since `hunt`/`brief`/`loop` read
as three views onto the same underlying capability and are not.

## BOUNDARIES CHECKED, NO DEFECT FOUND

- **`facts["deadline"]` cross-module contract** (the exact shape of bug
  already found and fixed once this session for NZ GETS). Re-checked
  end to end: `mouth_ted.py`, `tender_radar.py` (UK Contracts Finder),
  and `mouth_etenders_ie.py` all write `facts["deadline"]`;
  `mouth_gets_nz.py` writes `facts["close_date"]`;
  `brief.py::_DEADLINE_FACT_KEYS = ("deadline", "close_date")`
  (`brief.py:136`) and `hunt_loop.py::HuntEntrySnapshot.from_entry`
  (`hunt_loop.py:168`) both read only `facts.get("deadline", ...)`.
  This means a hypothetical future source that only writes `close_date`
  (like GETS) would reproduce the exact NZ-30-notices bug inside
  `hunt_loop.py` specifically — `brief.py` was patched for both keys,
  `hunt_loop.py` was not. **Currently harmless** because `hunt_loop.py`
  only ever calls single-source `hunt()` against TED (see Finding 2),
  which always writes `deadline`, never `close_date` — but if Finding 2
  is ever fixed by pointing the loop at `hunt_multi()`, this second
  fact-key mismatch reappears immediately for any NZ GETS notice the
  loop then sees. Recorded here rather than as a separate top-level
  finding because it is not live today, but it is a real landmine for
  whoever fixes Finding 2 next, and it's the same class of bug this
  session already burned time on once.
- **TED-shaped notice vs. flat `parse_items()`-shaped item** (the
  wrong-input-shape bug already found and fixed this session). Checked
  both `hunt.py::_assess_notice`'s TED path and
  `sources.py::_ted_signal_from_raw` — both now correctly re-shape via
  `mouth_ted.parse_items()` before calling `ted_signal()`, and both
  carry an explicit comment naming the original bug. No regression
  found.
- **Prose-criteria-ignored bug** (TED 244223-2024). Checked that
  `qualification.py::_no_code_of_type()` is reached from all four
  code-driven dimensions (`_assess_staff`, `_assess_certifications`,
  `_assess_insurance`, `_assess_references`) and downgrades to `INFO`
  whenever `elig.selection_criteria_description_text` is non-empty,
  regardless of which TED code triggered the check. Sound — this closes
  the class of bug, not just the one instance.
- **`QualificationResult`/`HuntEntry` band-integrity invariants** — both
  independently re-derive their own band from their own factors in
  `__post_init__` and refuse to construct a mismatched object
  (`qualification.py:281-318`, `hunt.py:218-228`). Verified these are
  real constructor-time checks, not decorative — tried constructing a
  mismatched `QualificationResult` mentally against the code and
  confirmed `QualificationIntegrityError` is unavoidable.
- **`sources.py`'s "criteria-less source" honesty rule** — verified
  `normalise_gets_nz`/`normalise_uk_contracts_finder` never set any
  `eligibility.py` criteria-shaped key, so a GETS/UK-CF notice can only
  ever land `INSUFFICIENT_DATA`, never `QUALIFIED`/`DISQUALIFIED`. Matches
  the module's own claim and `TestHonestyRule` in `test_sources.py`.
- **`mouth_common.fetch_feed()` gate wiring** — confirmed `hunt.py`,
  `sources.py`, and all four unwired mouths route their fetch through
  `fetch_feed()` with a real `DiscoveryPolicy`, never a second ungated
  socket.
- **Full test run**: `foundation.tests.test_hunt`, `test_hunt_loop`,
  `test_sources`, `test_brief`, `test_qualification`, `test_eligibility`,
  `test_operator_cli`, `test_mouth_bounty`, `test_mouth_gigs`,
  `test_mouth_etenders_ie`, `test_mouth_find_a_tender_uk` — 312 tests,
  all pass. Green, but green is exactly consistent with Finding 1: every
  one of those tests exercises a module in isolation; none of them
  assert that `sources.py`/`operator_cli.py`/`cron_pulse.py` actually
  call the four new mouths, because none of them do.
